# Spice & Food Processing — Business Management System

## Build Specification (Prototype v1)

---

## 0. Context & Design Principles

**Who uses this:** One person — the business owner. She makes spice blends and other food products, buys raw materials, produces batches, and sells to retail and wholesale customers.

**The core problem:** No visibility into stock, profit, or product performance. Everything lives in memory or a notebook.

**The core risk:** She forgets to enter data, the numbers drift, she stops trusting the system, she abandons it.

**Therefore, four non-negotiable design principles:**

1. **Speed over completeness.** Every entry action must be doable in under 20 seconds on a phone. If a form has more than 4 required fields, cut it down.
2. **Retroactive by default.** Assume she enters things later, not in real time. Every entry form has a date picker defaulting to today but freely changeable.
3. **Self-correcting.** Stock counts let her reset reality without the system being "broken." Missing entries create a discrepancy, never permanent corruption.
4. **Derived over entered.** She enters three things (purchases, batches, sales) plus expenses. Everything else — stock levels, profit, reports — is calculated. She never types a number the system could compute.

---

## 1. Architecture Decision: Is a separate "in-app area" needed?

**No. Go straight to the dashboard after login.**

Reasoning:

- There is exactly one user. There's no public-facing product, no marketing site, no customer portal, no role separation.
- A landing page → login → "app area" → "admin dashboard" hierarchy is structure borrowed from multi-tenant SaaS. Here it's pure friction and extra screens between her and the thing she came to do.
- The whole system _is_ the admin dashboard.

**Correct shape:**

```
/login  →  /  (dashboard)  →  everything else
```

If this ever becomes a product sold to other food processors, you add a marketing site and multi-tenancy then. Do not pre-build for it now.

**One caveat worth planning for:** structure the code so `businessId`/`ownerId` could be introduced later without a rewrite (keep data access behind a service layer rather than querying Prisma directly from route handlers). Don't implement multi-tenancy — just don't make it painful to add.

## 2. Entities

Full Prisma schema is in `schema.prisma`. Summary of entities and their roles:

| Entity                | Purpose                                     | Who/what changes it                                                     |
| --------------------- | ------------------------------------------- | ----------------------------------------------------------------------- |
| `User`                | Single owner login                          | Seeded once                                                             |
| `RawMaterial`         | Ingredients + packaging, with stock on hand | Increased by purchases, decreased by batches, corrected by stock counts |
| `RawMaterialPurchase` | Record of buying materials                  | Manual entry                                                            |
| `Product`             | Sellable finished good (per package size)   | Increased by batches, decreased by sales, corrected by stock counts     |
| `Recipe`              | Formula for one product                     | Set up once, edited rarely                                              |
| `RecipeIngredient`    | Line items of a recipe                      | Set up with recipe                                                      |
| `Batch`               | A production run                            | Manual entry                                                            |
| `BatchConsumption`    | Snapshot of materials used in a batch       | Auto-generated by batch creation                                        |
| `Customer`            | Repeat buyers (optional per sale)           | Manual, lightweight                                                     |
| `Sale`                | A sale transaction                          | Manual entry                                                            |
| `SaleItem`            | Line items on a sale                        | Part of sale entry                                                      |
| `Expense`             | Non-material costs                          | Manual entry                                                            |
| `StockAdjustment`     | Physical count corrections                  | Manual entry                                                            |

### Entities to ADD to the existing schema

```prisma
model User {
  id           String   @id @default(cuid())
  email        String   @unique
  passwordHash String
  name         String?
  createdAt    DateTime @default(now())
}

enum AdjustmentTarget {
  RAW_MATERIAL
  PRODUCT
}

model StockAdjustment {
  id             String           @id @default(cuid())
  targetType     AdjustmentTarget
  rawMaterialId  String?
  productId      String?
  systemQuantity Decimal          @db.Decimal(12, 3) // what the system thought
  countedQuantity Decimal         @db.Decimal(12, 3) // what she actually counted
  variance       Decimal          @db.Decimal(12, 3) // counted - system
  reason         String?          // "spillage", "forgot to log sale", "gift"
  adjustedAt     DateTime         @default(now())
}
```

Also add to `Sale`: `amountPaid Decimal` so partial payments are trackable alongside `paymentStatus`.

### 3.2 Dashboard (Home)

**Route:** `/`

The most important screen. Must answer, without scrolling on mobile: _is anything wrong, and how am I doing?_

**Sections, in order:**

1. **Quick Entry buttons** (large, thumb-reachable): `+ Sale` · `+ Purchase` · `+ Batch` · `+ Expense`
2. **Alerts strip** — low stock raw materials, low stock products, items nearing expiry, unpaid sales
3. **This month at a glance** — Revenue · Expenses · Estimated Profit
4. **Last entry indicator** — "Last sale logged: 3 days ago" (a visible nudge)
5. **Recent activity** — last 5–10 entries of any type

### 3.3 Quick Entry Flows

These are the highest-priority screens in the entire build. Treat them as the product.

| Flow         | Route            | Fields                                                                       | Target time |

| New Sale     | `/sales/new`     | Product + qty (repeatable rows), customer (optional), amount paid, date      | < 20s       |
| Log Purchase | `/purchases/new` | Raw material, quantity, total cost, supplier (optional), date                | < 20s       |
| New Batch    | `/batches/new`   | Product (recipe auto-loads), quantity to make, date, expiry (auto-suggested) | < 20s       |
| Add Expense  | `/expenses/new`  | Category (dropdown), amount, date, note                                      | < 15s       |

**UX requirements for all four:**

- Date defaults to today, one tap to change
- Most recently used items sorted to the top of every picker
- Quantity steppers (+/−) alongside numeric input
- "Save & add another" button in addition to "Save"
- Batch form shows a live **ingredient availability check** before submit: green if enough stock, warning if short (but still allow saving — she may have bought materials without logging them)

### 3.9 Stock Count / Adjustments

**Route:** `/stock-count`

The reconciliation safety valve. Critical for long-term trust.

- Select raw materials or products
- Shows system quantity next to an input for counted quantity
- Computes variance, optional reason
- Saving writes a `StockAdjustment` and updates the entity's `quantityOnHand` to the counted value

**Route:** `/stock-count/history` — past adjustments and variances (useful for spotting systematic under-logging).

## 4. Functional Requirements

### FR-1 — Authentication

- Single seeded user, email + password
- Sessions long-lived (30 days) to minimize re-login friction
- All routes except `/login` protected

### FR-2 — Raw Material Stock Integrity

- `quantityOnHand` increases **only** via `RawMaterialPurchase`
- Decreases **only** via `BatchConsumption`
- Corrected **only** via `StockAdjustment`
- Never directly editable through a form

### FR-3 — Product Stock Integrity

- Increases **only** via `Batch`
- Decreases **only** via `SaleItem`
- Corrected **only** via `StockAdjustment`

### FR-4 — Batch Production (transactional)

Creating a batch must, in a **single database transaction**:

1. Load the recipe and compute scale = `quantityMade / recipe.yieldQty`
2. For each ingredient: decrement `RawMaterial.quantityOnHand` by `ingredient.quantity × scale`
3. Write a `BatchConsumption` row per ingredient (snapshot, not a reference to the live recipe)
4. Increment `Product.quantityOnHand` by `quantityMade`
5. Generate batch number and expiry date

Negative stock is **allowed with a warning**, not blocked — real life runs ahead of data entry. Flag it in the UI instead.

### FR-5 — Sale Recording (transactional)

1. Create `Sale` + `SaleItem` rows
2. Decrement each `Product.quantityOnHand`
3. Compute `totalAmount` from line items; set `paymentStatus` from `amountPaid`

### FR-6 — Cost Computation

- `RawMaterial.averageCost` recalculated on each purchase (weighted average)
- Product material cost = Σ (ingredient qty × material averageCost) ÷ yield
- Product margin = `sellingPrice` − material cost per unit

### FR-7 — Alerts

Computed on dashboard load:

- Raw material at or below `reorderThreshold`
- Product at or below its low-stock threshold
- Batch expiring within 30 days
- Sale unpaid for more than 14 days
- No entries logged in the last 3 days

### FR-8 — Retroactive Entry

Every create form accepts a user-set date, past or present. No entry is locked to "now."

### FR-9 — Stock Reconciliation

Stock counts overwrite computed quantities and log the variance. Never silently discard the discrepancy.

### FR-10 — Reminders (v1.5)

Optional daily push/SMS/WhatsApp nudge if no entries logged that day. Ship v1 without it; the dashboard "last entry" indicator covers the gap initially.

---

## 5. Non-Functional Requirements

- **Mobile-first.** She will use this on a phone, almost exclusively. Design at 375px width first; desktop is secondary.
- **Offline tolerance (v2).** Nice-to-have: queue entries locally if connectivity drops.
- **Currency:** NGN, formatted with thousands separators.
- **Decimals:** all quantities and money as `Decimal`, never floats.
- **Timezone:** Africa/Lagos.
- **Performance:** dashboard must load in under 2s on mobile data.

## 6. Suggested Stack

Aligned with your existing stack:

- **Next.js 15** (App Router) — full-stack, server actions for mutations, no separate API needed at this scale
- **PostgreSQL + Prisma**
- **Tailwind CSS** + shadcn/ui
- **Auth.js** (credentials provider) or Lucia — single user, keep it simple
- **Recharts** for report charts
- **Deployment:** Vercel + Neon/Supabase Postgres

A separate NestJS backend is unnecessary here — one user, one client, no external consumers. Next.js server actions keep the whole thing in one deployable.

## 7. Build Order

**Phase 1 — Foundation**

1. Schema + migrations + seed (user, expense categories, units)
2. Auth + protected layout + navigation shell

**Phase 2 — Master data** 3. Raw materials CRUD 4. Products CRUD 5. Recipe editor

**Phase 3 — The core loop (highest value)** 6. Log Purchase 7. New Batch (with transaction logic) 8. New Sale 9. Add Expense 10. Dashboard with alerts and quick-entry buttons

**Phase 4 — Trust & insight** 11. Stock count / adjustments 12. Reports 13. Customers 14. Settings

**Phase 5 — Polish** 15. Reminders 16. CSV export 17. Offline queueing

Ship Phase 3 to her and let her use it for two weeks before building Phase 4. What she actually touches will tell you what to build next — and what to delete.

## 8. Open Questions to Resolve With Her

1. Does she sell the same product in multiple package sizes? (Determines whether `Product` = blend, or blend × size)
2. Does she ever sell raw/unprocessed items directly, without a production step?
3. Are there recurring wholesale customers with credit, or is it mostly cash-and-carry?
4. Does she track expiry today, or is it a new discipline this system would introduce?
5. Roughly how many sales a day? (Determines whether per-sale entry or daily-summary entry is the right primary flow)
